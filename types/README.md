# Type System Documentation

## Overview

This directory contains the centralized type system for the Art by Romi application. The type system is designed to eliminate duplication, provide type safety, and enable runtime validation.

## Directory Structure

```
types/
├── generated/              # Auto-generated types (DO NOT EDIT)
│   ├── sanity.types.ts    # Generated by Sanity typegen
│   └── database.types.ts  # Generated by Supabase CLI (when configured)
├── core/                  # Base domain types
│   ├── product.ts         # Core product types
│   ├── cart.ts           # Core cart types
│   ├── order.ts          # Core order types
│   ├── customer.ts       # Core customer types
│   └── pricing.ts        # Core pricing types
├── api/                   # API-specific types
│   ├── requests.ts       # API request types
│   ├── responses.ts      # API response types
│   └── mercadopago.ts    # Payment provider types
├── ui/                    # UI-specific types
│   ├── forms.ts          # Form data types
│   └── components.ts     # Component prop types
├── database/              # Database types and mappers
│   ├── tables.ts         # Database table types
│   └── mappers.ts        # DB <-> Application type mappers
├── validators/            # Zod schemas for runtime validation
│   ├── checkout.ts       # Checkout form validation
│   ├── cart.ts          # Cart item validation
│   ├── order.ts         # Order validation
│   └── product.ts       # Product validation
└── index.ts              # Main barrel export
```

## Usage Guidelines

### 1. Never Edit Generated Types

Files in the `generated/` directory are automatically generated and should never be edited manually. Any changes will be overwritten on the next generation.

### 2. Use Core Types as Base

Core types define the fundamental domain models. Extend these for context-specific needs:

```typescript
import { BaseCartItem } from '@/types/core/cart';

// Database-specific extension
interface DBCartItem extends BaseCartItem {
  id: string;
  created_at: string;
}
```

### 3. Validate External Data

Always validate data from external sources (API requests, database queries, etc.):

```typescript
import { validateCartItem } from '@/types/validators/cart';

// In API route
export async function POST(req: Request) {
  const body = await req.json();
  
  try {
    const validatedItem = validateCartItem(body);
    // Process validated data
  } catch (error) {
    // Handle validation error
  }
}
```

### 4. Use Type Guards

Type guards help with type narrowing:

```typescript
import { isValidCartItem } from '@/types/validators/cart';

if (isValidCartItem(data)) {
  // TypeScript knows data is CartItem here
  console.log(data.cartItemId);
}
```

### 5. Import from Index

For most use cases, import types from the main index:

```typescript
import { CartItem, Product, Order } from '@/types';
```

## Type Generation Commands

### Sanity Types

Generate types from Sanity schemas:

```bash
npm run typegen
```

This is automatically run before `dev` and `build` commands.

### Database Types (Supabase)

Generate types from the remote Supabase project:

```bash
npm run typegen:supabase
```

For local development (requires Docker):

```bash
npx supabase gen types typescript --local > types/generated/database.types.ts
```

### Generate All Types

Generate both Sanity and Supabase types:

```bash
npm run typegen:all
```

## Common Patterns

### Extending Generated Types

```typescript
// types/core/product.ts
import { Product as SanityProduct } from '@/sanity.types';

// Use Sanity type as base
export type Product = SanityProduct;

// Extend for UI needs
export interface ProductWithCalculatedPrice extends Product {
  finalPrice: number;
  discount?: number;
}
```

### Creating Validators

```typescript
// types/validators/custom.ts
import { z } from 'zod';

export const customSchema = z.object({
  field: z.string(),
  // ... other fields
});

export type ValidatedCustom = z.infer<typeof customSchema>;

export function validateCustom(data: unknown): ValidatedCustom {
  return customSchema.parse(data);
}
```

### Type Mapping

```typescript
// When converting between contexts
import { dbOrderToOrder } from '@/types/database/mappers';

const dbOrder = await supabase.from('orders').select().single();
const order = dbOrderToOrder(dbOrder);
```

## Migration Guide

When migrating existing code to use the new type system:

1. Replace local type definitions with imports from `@/types`
2. Add validation for external data inputs
3. Use generated types for Sanity data
4. Apply type mappers when converting between contexts

## Type Safety Checklist

- [ ] All API endpoints validate input data
- [ ] Sanity queries use generated types
- [ ] Database operations use type mappers
- [ ] No duplicate type definitions
- [ ] External data is validated before use
- [ ] Type guards are used for runtime checks

## Troubleshooting

### Type Generation Fails

If Sanity type generation fails:
1. Check that schemas are valid
2. Run `sanity schema extract --enforce-required-fields`
3. Fix any schema errors reported

### Type Mismatches

If you encounter type mismatches:
1. Regenerate types: `npm run typegen`
2. Check that you're using the correct type context
3. Use type mappers when crossing boundaries

### Validation Errors

For validation errors:
1. Check the error message for specific field issues
2. Ensure data matches the expected schema
3. Use `.safeParse()` for graceful error handling

## Best Practices

1. **Single Source of Truth**: Each type should have one canonical definition
2. **Context-Aware Types**: Use appropriate types for each context (UI, API, DB)
3. **Runtime Safety**: Validate all external data
4. **Type Generation**: Keep generated types up-to-date
5. **Documentation**: Document complex type relationships
